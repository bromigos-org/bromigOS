# bromigOS core

This folder is the Rust core of bromigOS. It builds the `bromigos` command and the
libraries behind it. The core holds the rules that would otherwise be copied between Bash
and Python, such as finding the live Hyprland session or reading the animation switches.
Python tools ask the binary for its `--json` output instead of keeping their own copy.

## How it's organised

The workspace has three crates.

| Crate | What it holds |
|---|---|
| `crates/bromigos-core/` | The library. One module per area: session, config, anim, profile, theme, lock, ipc, commands, migrate, update, snapshot, boot, channel, install, setup, targets, create, peripheral, hw, accessibility, idle, paths. |
| `crates/bromigos-art/` | The art pipeline: `art.toml`, pricing, the nolgia SDK, the ComfyUI backend, the defaults for `create.toml` and `targets.toml`, and the job log. |
| `crates/bromigos/` | The `bromigos` binary. It parses arguments with clap and holds the setup screens, `mute`, `target`, `art make` and `idle`. |

The GPU table, `crates/bromigos-core/data/gpu-ids.tsv`, is generated by
`tools/hw/gpu-tables.py`. [docs/hardware.md](../docs/hardware.md) explains it.

The package `bromigos-core` installs the binary as `/usr/bin/bromigos`. It also ships the
themes, the theme templates, the shared Python libraries in [`lib/`](../lib/README.md)
and the migrations. [packaging/README.md](../packaging/README.md) lists the rest.

## Building and testing

From this folder:

```bash
cargo build                                  # builds target/debug/bromigos
cargo test
cargo fmt --check
cargo clippy --all-targets -- -D warnings
```

The package build runs `cargo test --frozen --all-features` in its `check()` step. Commit
`Cargo.lock` with any dependency change.

After you change a command's help text, run `tools/docs/generate.py` from the repository
root. It rewrites the manual's [Commands](../manual/src/commands.md) page from the help.
CONTRIBUTING.md has the details.

## How the commands work

The manual's [Commands](../manual/src/commands.md) page lists every option, as `--help`
prints it. This section covers what `--help` doesn't say: what each command does inside,
in what order, and which files it touches.

Pass-through commands (`live`, `vector`, `wallpaper`) exec their target. The exit code,
output and signals are the target's own. A target that can't be run gives exit 127.

### The session

`bromigos session` finds the live Hyprland session. It prints `WAYLAND_DISPLAY=…` and
`HYPRLAND_INSTANCE_SIGNATURE=…`, and exits 1 when there's no session.

- `session import` also runs `dbus-update-activation-environment --systemd` with those
  two variables.
- `session exec CMD…` imports, then execs `CMD` with the two variables set. With no
  session it still execs `CMD`, with the environment unchanged.
- `session adopt` runs at login. It imports, then stops VECTOR's daemon if that daemon
  belongs to another session. It tries `bromigos-holo stop now` first, then `kill`. It
  prints nothing unless you pass `--json`.

`session hold` and `session release` protect Hyprland during a package transaction.
pacman runs them through two hooks that bromigos-core installs:
`bromigos-hypr-hold.hook` and `bromigos-hypr-release.hook`. They fire only when a
transaction changes `usr/share/bromigos/default/hypr/*`.

- `hold` turns `misc.disable_autoreload` on in every running Hyprland in scope. As root
  that's every user's session, with `hyprctl` run as that user. Anyone else holds only
  their own.
- It records each old setting, keyed by the compositor's PID and start time. Root
  records go in `/run/bromigos/hypr-hold/`, a user's in
  `$XDG_RUNTIME_DIR/bromigos-hypr-hold/`. A second hold keeps the first one's value.
- With `--pacman`, `hold` is silent when no Hyprland runs and always exits 0. It also
  starts a detached watcher. If pacman exits without running the release hook, the
  watcher releases what's still held.
- `release` checks each held Hyprland with `Hyprland --verify-config`, as its user. If
  the config verifies, it runs `hyprctl reload` once, then `hyprctl configerrors`. Then it
  puts auto-reload back as it was. A config that doesn't verify isn't reloaded.
- With `--pacman`, `release` covers every running Hyprland, held or not, and always
  exits 0. Without it, `release` exits 1 when one wasn't reloaded cleanly.

Hold, release and the watcher take turns on a `.lock` file beside the records.
[docs/update.md](../docs/update.md) explains why the hold exists.

### Updating, channels and rollback

`bromigos update` runs these steps in order.

1. It takes a pre snapshot with `snapper create`, described as "bromigos update".
2. It runs `sudo pacman -Syu` in your terminal. The prompts, sudo and any security key are
   yours to answer. It sets `SNAP_PAC_SKIP=y`, so snap-pac doesn't take a second pair.
3. It updates AUR packages with `paru -Sua`, when pacman succeeded, the AUR is on and
   `paru -Qua` lists something ([docs/aur.md](../docs/aur.md)). paru's own pacman runs
   keep `SNAP_PAC_SKIP=y` through `--sudoflags --preserve-env=SNAP_PAC_SKIP`.
4. It takes the post snapshot. If nothing changed, it deletes the pair, retrying for up
   to 10 seconds while snapperd still holds the configuration.
5. It runs the pending migrations, described under [Migrations](#migrations).
6. It renders the theme in force again. It also starts redrawing any out-of-date theme
   switcher previews in the background, and runs `bromigos boot theme apply`.
7. It restarts whatever runs older code than is installed, as `bromigos restart` does.

If pacman fails, the update stops there with pacman's exit code. A failed migration stops
it with exit 1. A failed AUR step makes it exit 1 too, but only after every other step
has run.

- `--check` changes nothing. It lists the upgrades waiting (from `checkupdates`, in
  pacman-contrib), the pending migrations, the restarts needed, how updates are
  snapshotted here, and the updates that can be undone. Without `checkupdates` it says it
  can't tell.
- `--no-packages` runs only the steps after the packages.
- `--no-aur` leaves the AUR out this time. With `--check`, it leaves the AUR's updates
  out of the list.
- `--yes` doesn't ask. pacman gets `--noconfirm`, the AUR step builds without paru's
  review, and a rollback goes ahead without a question.
- `--rollback [PRE]` undoes an update. It runs `snapper undochange PRE..POST` on the pair
  recorded around it, which is the newest pair unless you name its pre snapshot. It shows
  the packages and files first and asks. `--yes` skips the question, and `--json` needs
  `--yes`. The rollback is recorded too.
- `--channel NAME` switches the channel, then updates. Moving to an older channel needs
  `--downgrade`, which runs `pacman -Syuu` so newer packages go back.

Each update is recorded in `~/.local/state/bromigos/updates.jsonl`.

`bromigos aur` manages the AUR helper ([docs/aur.md](../docs/aur.md)).

- `status`, the default, reports three things. The setting is `enabled` in
  `~/.config/bromigos/aur.toml`, true by default. The helper is paru, from
  `paru --version`, else yay. It's bromigOS's build when pacman's Packager field says so.
  Last come the AUR updates waiting.
- `on` turns the setting on, then runs `ensure`.
- `off` turns the setting off. It removes the paru bromigOS installed, with
  `sudo pacman -R paru`, and never a helper you installed. bromigOS records its own
  install in `~/.local/state/bromigos/aur.toml`.
- `ensure` runs `sudo pacman -S --needed paru`, unless the AUR is off, a helper is
  installed, or a package provides `paru`. It exits 75 when paru isn't in the synced
  repositories yet. `bromigos install` and a migration run it.

`bromigos channel` shows or switches the channel this machine follows: `stable`, `rc`,
`edge` or `dev`. The channel is the `Server` line of the `[bromigos]` section in
`/etc/pacman.conf`. It also reads a server from the mirrorlist named by an
`Include` in that section. A channel switch replaces the include with an explicit
server and leaves the packaged mirrorlist unchanged.

- To switch, it rewrites that line and its `SigLevel` with `sudo install`.
- It deletes the old channel's sync database, so the next `pacman -Sy` fetches the new
  one. The JSON reports this as `dropped`.
- `--repo` gives the base URL when it isn't known, such as after `dev`, or when it
  changes.
- `dev` points at a local repository that `packaging/dev-repo.sh` builds.

`bromigos rollback` sets up and reports the snapshots behind `update --rollback`.

- `status` says how this machine snapshots updates. It covers btrfs, snapper, snap-pac,
  the boot menu, and whether you may list root's snapshots. It also lists the updates
  that can be undone, and what `setup` still has to do.
- `setup` installs what's missing where `/` is btrfs. That's snapper's `root`
  configuration with wheel allowed to list it, snap-pac, and on GRUB, grub-btrfs with its
  daemon and the `grub-btrfs-overlayfs` hook. On limine it adds limine-snapper-sync when a
  repository has it. It keeps a separate `@.snapshots` subvolume. Inside an install chroot,
  snapper runs with `--no-dbus`. `bromigos install` runs this step too.
- `allow` lets wheel, and you if you're not in wheel, list root's snapshots, so updates
  can be recorded. It runs `sudo snapper get-config`, then `set-config` with what's
  missing.

`bromigos boot theme` manages bromigOS's GRUB theme in the current theme's colours. The
code is `boot.rs`, and [docs/boot.md](../docs/boot.md) describes the theme.

- `status` names the boot loader. Only GRUB is themed. systemd-boot and limine are left
  alone. It says whether the theme is on, which means bromigOS's block is in
  `/etc/default/grub`. It reads what's in `/boot` from `/var/lib/bromigos/boot/state.json`
  and says whether that's what the current theme wants.
- `on` copies the theme into `/boot`, adds the block and makes `grub.cfg` again, through
  `sudo /usr/lib/bromigos/boot/bromigos-boot-theme on`. With `--auto`, it does nothing
  where you turned it off. Install, setup and a migration use `--auto`.
- `apply` brings `/boot` up to date where the theme is on. `update` runs it, and so does
  the `boot` theme-set hook with `--no-prompt`. That runs `sudo -n`, so when a password
  would be needed it waits for the next update.
- `off` takes the block out, makes `grub.cfg` again and removes the theme. It stays off.

`bromigos restart` restarts each running piece whose package was installed after the
process started. It reads pacman's install dates for this. A piece whose default config
is newer is reloaded instead.

| Piece | How it restarts |
|---|---|
| The live layer | `bromigos-live restart` |
| The widgets, waybar, dunst | Stopped, then started again in the session with `setsid` |
| VECTOR and his voice server | `bromigos-holo restart` |
| The OSD | `swayosd-server`, also started with the theme's style when it's installed but not running |
| hypridle (`idle`) | The policy rendered again, then hypridle started through Hyprland's `exec` |
| dunst's config | `dunstctl reload` |

waybar is always restarted, never sent `SIGUSR2`, because that signal can crash it.
hypridle also restarts when its policy renders differently, or when a file it reads
changed after it started. A newer Hyprland or kernel is reported, not acted on. You log
out or reboot.

A new kernel or NVIDIA driver that waits for a restart of the computer
(`bromigos-core/src/reboot.rs`) holds back the pieces that need the GPU: the live layer
and VECTOR. Their need becomes `reboot`, and they keep running on the libraries they
loaded. A `driver` or `kernel` line says what waits. `bromigos update` then skips the
theme previews, ends with a line asking for the restart, and sends one notification
([docs/update.md](../docs/update.md#when-the-kernel-or-the-graphics-driver-changes)).

`bromigos restart NAME…` restarts the named pieces, stale or not. The names are `live`,
`widgets`, `waybar`, `dunst`, `osd`, `vector`, `idle` and `hyprland`. For `hyprland` it
runs `hyprctl reload`.

### Themes and the look

`bromigos theme set [NAME]` renders a theme. With no name it renders the current one.

1. It renders the templates into `~/.local/state/bromigos/theme/current/`. That includes
   `palette.json`, the recoloured bar icons in `icons/`, and the emblem kit. It writes to a
   new folder and swaps it in atomically.
2. It tells the running apps. It restarts waybar, sends kitty `SIGUSR1`, and runs
   `hyprctl reload` and `dunstctl reload`. It tells the live layer on its socket. The
   widgets, VECTOR and the decks watch `palette.json` themselves. gtklock, rofi and Qt
   apps pick the theme up when they next start.
3. It runs the theme-set hooks. Packaged hooks come first, then
   `~/.config/bromigos/hooks/theme-set.d/*`. A user's hook replaces a packaged one of the
   same name.

An unknown name exits 1 and writes nothing. `--no-reload` skips step 2.
[docs/theming.md](../docs/theming.md) describes themes and templates.

The other `theme` verbs:

- `list` shows every theme, first-party and yours, with `*` on the current one.
- `current` prints the theme in force. That's `wick` when none was ever set.
- `install SOURCE` is `bromigos ext install`. `--force` moves aside a theme of yours with
  the same name.
- `remove NAME` removes an extension's theme through `bromigos ext remove`, or deletes one
  of yours. It never removes a first-party theme or the one in force.
- `new NAME` makes a theme extension to edit in `./NAME`. It starts from the starter, or
  from another theme's files with `--from`. Its switcher preview is drawn in the
  background.

`bromigos anim` lists every animation of the live layer and whether it's on. A `*` marks
the ones your own switch decides. `anim on|off NAME…` writes your switches, and
`anim reset` removes them. An unknown name exits 1 and writes nothing. The switches live
in `~/.config/bromigos/live/overrides.toml`, edited with `toml_edit` so your comments and
order stay.

`bromigos accessibility`, or `a11y`, holds two settings in
`~/.config/bromigos/accessibility.toml`. [docs/accessibility.md](../docs/accessibility.md)
describes them.

- `motion full|reduced|still` and `contrast normal|high` write the setting with
  `toml_edit`. Then they render the current theme again, with the colours made
  high-contrast or the motion level written into its `hyprland.lua` and `palette.json`.
- Inside a live session, and unless you pass `--no-reload`, they tell the apps. Contrast
  reloads as `theme set` does. Motion runs `hyprctl reload`, the live layer's `reload`,
  and sets GTK's `enable-animations`.
- An unknown level exits 2 and writes nothing.
- `check [THEME]` measures a theme's colours against high contrast's targets, both as
  designed and made high-contrast. It exits 1 when the high-contrast colours fall short.

`bromigos mute` is the desktop's one mute switch. It covers the theme's sounds and
VECTOR's voice. It sets each through that program's own `mute` command, so a running
daemon hears it at once. The live layer's `muted` setting also silences its codec calls.
`toggle`, which the keys use, mutes everything if anything is unmuted.

### Extensions

`bromigos ext` installs extensions: themes, decks, panels, VECTOR's tools and skills,
homelab adapters, commands and hooks. [docs/extensions.md](../docs/extensions.md)
describes them. This is what happens inside.

- `install` takes a Git URL, a folder or a catalog name. It checks the source out at one
  commit into `~/.local/share/bromigos/ext/src/<name>`. It links the parts into
  `~/.local/share/bromigos/ext/active/<seam>/` and records everything in the ledger,
  `~/.local/state/bromigos/ext/ledger.json`.
- A theme installs without a question, and its switcher preview is drawn in the
  background. Anything else prints its plan and permissions and waits for a yes typed at
  a terminal. There's no `--yes`. The only unattended way is `bromigos setup --answers`
  with `[extensions] approve = true`.
- `update` fetches the branch. A tag or commit stays pinned until you pass `--ref`. It
  shows the files added, changed and removed, any new permissions, and any hand edits it
  would replace. Then it asks, except for themes. It swaps the checkout in one step with
  `renameat2(RENAME_EXCHANGE)` and relinks.
- `remove` deletes the links and the checkout. The ledger keeps a line. `disable` unlinks
  the parts, and `enable` relinks them after checking every file. None of them touches
  the theme in force.
- `list --verify` checks every file against the ledger. `info` shows one extension, or
  what a source would install without installing it.
- `new KIND NAME` writes a working starter. `validate` checks a folder as `install`
  would.
- `search` lists the catalogs' extensions. `migrate` turns themes copied in by the old
  `theme install` into extensions, when a catalog has them file for file.

### Install, setup and hardware

`bromigos install` is the installer that `install.sh` hands over to. Its steps, in order,
are: preflight, packages, services, rollback, hardware, configs, desktop settings, theme
and boot menu. Then it runs `bromigos setup`. [docs/install.md](../docs/install.md)
describes each step.

`bromigos setup` asks the first-run questions in a terminal UI built with ratatui. It can
also read answers from a file or from flags. The sections are monitors, hardware,
accessibility, theme, vector, voice, homelab, targets, create and peripherals.
[docs/install.md](../docs/install.md) describes each one and the answers file.

`bromigos setup homelab` is special. When `bromigos-homelab` is installed, it runs that
package's detector, `bromigos-setup-homelab`, with its own flags
([docs/homelab.md](../docs/homelab.md)). With `--homelab FILE` or `--answers FILE` it's
the built-in setup instead, which copies the file into place.

`bromigos hw` describes this machine's hardware and what `hw setup` would do.
[docs/hardware.md](../docs/hardware.md) has the full detail.

- Detection reads files only, never runs a command. `BROMIGOS_FS_ROOT` moves `/`, so a
  folder of fixture files can stand in for a machine.
- The plan asks `pacman -T` and `systemctl is-enabled` what's already there.
- `hw setup` changes only what differs. It installs the GPU's packages, but never swaps an
  installed NVIDIA driver. It writes system files with `sudo install`, runs
  `mkinitcpio -P` when the initramfs changes, and enables a laptop's
  `power-profiles-daemon`. Last, it writes `~/.local/state/bromigos/hw/hyprland.lua`.
- `--user-only` writes only that last file, with no sudo.
- Any other word goes to the router as `bromigos-hw-<name>`.

`bromigos peripheral` manages optional device modules, such as a Razer keyboard's macro
keys, dial and lighting. [docs/peripherals.md](../docs/peripherals.md) describes them.

- `list` shows every module and whether its device is connected. Packaged modules live in
  `$BROMIGOS_SHARE_DIR/peripherals/<id>/`, and yours in
  `~/.config/bromigos/peripherals/<id>/`. It finds devices in `/proc/bus/input/devices`
  and by the HID driver bound.
- `enable ID` installs the module's packages with `sudo pacman -S --needed` and adds you
  to its groups. It records `[ID] enabled = true` in
  `~/.config/bromigos/peripherals.toml`.
- Then it writes the Hyprland part to `~/.local/state/bromigos/peripherals/hypr.lua`. It
  turns auto-reload off, checks the config with `Hyprland --verify-config`, reloads once
  and reads `configerrors`. If the config doesn't verify, the old file goes back.
- Last, it starts the module's user services and `bromigos-peripherals.service`, or
  restarts the service so it reads the change.
- `enable` exits 1 when the device isn't connected, unless you pass `--force`.
- `follow ID vector|theme` sets what the lighting follows. The daemon picks it up within
  its 10-second poll.
- `disable` turns a module off. Its packages stay. The daemon stops with the last module.
- `refresh` writes the Hyprland part again. Hyprland reloads only when it changed.

### Idle and lock

`bromigos idle` manages the idle policy: when the screensaver starts, the screen locks,
the displays go off and the machine suspends. [docs/idle.md](../docs/idle.md) describes
the policy.

- `status` shows the policy in plain words. Your file, `~/.config/bromigos/idle.toml`, is
  layered over `/usr/share/bromigos/default/idle.toml`. A `*` marks each timer your file
  sets. It also shows the matching preset, stay-awake, hypridle, and any warnings.
- `set`, `preset` and `undo` change your file with `toml_edit` and keep the old one for
  `undo`. Then they render `~/.local/state/bromigos/idle/hypridle.conf`, if it changed,
  and restart this session's hypridle. A value out of range exits 1 and writes nothing.
- The presets are `default`, `screensaver-only` and `presentation`.
- `stay-awake` holds a logind idle inhibitor, `systemd-inhibit --what=idle`, in its own
  process group. It's recorded in `$XDG_RUNTIME_DIR/bromigos-idle-awake.json`. `off` stops
  that group.
- `hook` points `~/.config/hypr/hypridle.conf` at the rendered policy. It replaces the
  packaged source line and keeps your own listeners, after a backup. A migration runs it.
- `render` prints the config the policy renders to.
- `start` is Hyprland's autostart. It renders the policy, then execs hypridle. With
  `--detach` it starts hypridle through the compositor instead, unless this session's
  already runs.

`bromigos lock` runs `loginctl lock-session`. hypridle then runs its `lock_cmd`, which is
`bromigos lock-run`.

`bromigos lock-run` runs a screen locker until you unlock. It tries `gtklock`, then
`hyprlock`. `BROMIGOS_LOCKER="a b"` replaces the list, one command per word.

- When the locker exits 0, you've unlocked, and `lock-run` exits 0.
- Any other exit, such as a crash or a kill, restarts the locker after half a second.
  Hyprland's `misc.allow_session_lock_restore` lets the new locker take over.
- A locker that fails twice in a row within 3 seconds of starting gives way to the next
  one in the list.
- Only one runs at a time. It holds an `flock` on `$XDG_RUNTIME_DIR/bromigos-lock.flock`,
  which the locker inherits. A second call does nothing and exits 0.
- It logs with `logger -t bromigos-lock` and gives up after 30 tries, with exit 1.
- It never unlocks anything and never signals a locker. `SIGUSR1` unlocks hyprlock.

### VECTOR, AI and art

`bromigos profile` holds who you are and what VECTOR calls you, in
`~/.config/bromigos/profile.toml`.

- `set name|full_name|pronouns VALUE` sets one field. `""` clears it.
- `address add|remove|set` edits the forms of address, most preferred first. `alias`
  edits the other names you go by.
- A value is one line of at most 80 characters, with no control characters, because it
  reaches VECTOR's prompt. Anything else exits 1 and writes nothing.
- A value that starts with `-` goes after `--`, as in `bromigos profile alias add -- -x-`.

`bromigos target` decides where AI work runs: on your homelab, on this machine or in the
cloud. It applies per service: the creation capabilities, `voice.tts`, `voice.stt` and
`llm`. [docs/targets.md](../docs/targets.md) describes it.

- With no verb it shows each service and the target it would use now, probing for a few
  seconds at most. `check` probes every target of every service, and `probe SERVICE…`
  probes some. Addresses are never printed.
- `homelab`, `local` or `cloud` puts that target first in `~/.config/bromigos/targets.toml`,
  globally or with `--only SERVICE`. The others keep their places. The cloud is never
  added by choosing another target. `--exclusive` uses that target alone.
- `order T…` sets the exact order. `reset` drops the services' own orders.
- `resolve SERVICE --json` prints what a service tries, in order, without probing. VECTOR
  asks this. Its document is `{"schema", "service", "configured", "order", "entries":
  [{"target", "engine", "endpoint"?, "key_file"?}]}`. `configured` is false when you have
  no `targets.toml`.

`bromigos art` makes a world's art. [docs/art.md](../docs/art.md) describes the pipeline.

- `status WORLD` reads the world's recipe and log. Each asset is `done`, `missing`,
  `stale`, `pending` or `new`. It also reports which backends could take a job. That
  means whether nolgia's credentials are found, and a 4-second probe of each ComfyUI.
- `plan WORLD` says what a run would make and the exact credits, from nolgia's live
  catalog. It exits 1 if the catalog refuses an asset.
- `run WORLD` makes it through the nolgia SDK, writes the outputs and logs each job to
  `themes/WORLD/art.log.jsonl`. A run over `--max-credits` is refused before anything is
  spent, with exit 3. A failed job exits 1.
- `make CAPABILITY --out FILE` makes one thing outside any world, through `create.toml`'s
  providers or the targets. VECTOR's `create` tool and hologram builder call it.
- `mark WORLD ASSET` records an asset made elsewhere as made with its current recipe.

### Status, commands and pass-through

- `bromigos status` reports the session, the live layer, VECTOR and the animations. It
  asks the daemons' sockets directly and never starts anything.
- `bromigos commands` lists the built-ins and every external command found, by group.
  `--all` includes hidden ones. `--check` lints them, described under
  [The command router](#the-command-router).
- `bromigos live on|off` asks the live layer for its `state` and sends `toggle` only if
  needed. It exits 1 if the live layer isn't running. Any other `live` arguments go to
  `bromigos-live`, and no arguments means `status`.
- `bromigos vector …` execs `bromigos-holo`, and `bromigos wallpaper …` execs
  `bromigos-wallpaper`.

## The command router

Built-ins come first. Any other `bromigos <group> <name> [args…]` runs an external
command. The router looks for an executable named `bromigos-<group>-<name>` in these
folders, in order:

1. `/usr/lib/bromigos/bin`
2. installed extensions' commands, in `~/.local/share/bromigos/ext/active/bin`
3. each folder on `PATH`

If none is found, it runs the group's root, `bromigos-<group>`, with `<name> [args…]`.
Names are lowercase words and digits joined by `-`. The first word is the group, so
`bromigos-toggle-night-light` is `bromigos toggle night-light`.

A built-in owns only its own words. `anim on|off|reset` is built in, but
`bromigos anim fade` reaches `bromigos-anim-fade`. The same goes for `profile`, `session`,
`art`, `peripheral` and `accessibility`. `live`, `vector`, `wallpaper` and `help` pass
everything through, so they own their whole group.

The groups, by purpose: `toggle`, `restart`, `launch`, `capture`, `setup`, `install`,
`refresh`, `theme`, `anim`, `hw`, `update`, `vector`, `live`, `session`, `lock`,
`commands`, `profile`, `art`, `channel`, `rollback`, `boot`, `ext`, `peripheral`, `idle`,
`private`, `secrets`, `emblem` and `storage`.

`bromigos storage` is the core package's Python command in `bin/bromigos-storage`.
It reads local drive state by default. Its saved plans, journals and migration rules
live in `lib/bromigos_storage*.py`. Status groups shared filesystems; cleanup discovers
Snapper and btrbk snapshots and applies explicit retirement plans with logs.
Provisioning, copying, switching and cleanup execution require explicit
terminal elevation; the command never opens an authentication window. See
[the storage reference](../docs/storage.md).

Other packages add commands this way. For example, `bromigos settings` is
bromigos-desktop's `bromigos-settings`, and `bromigos lab` is bromigos-homelab's
`bromigos-lab`.

bromigos-core installs these external commands of its own in `/usr/lib/bromigos/bin`:

| Command | What it does |
|---|---|
| `bromigos private decrypt\|edit\|status\|seed-profile` | Manages your private overlay: values kept encrypted with sops and age in your dotfiles, decrypted to `~/.config/bromigos/private/` at login |
| `bromigos secrets sync\|status` | Refreshes secret files from Vault, as the overlay's `secrets:` manifest lists. It never prints a value. |
| `bromigos emblem build --theme DIR` | Builds a theme's emblem kit ([docs/theming.md](../docs/theming.md)) |
| `bromigos install extension`, `bromigos remove extension` | The menu's rows for installing and removing an extension |
| `bromigos terminal` | Runs a command in your terminal, for the app launcher's entries |

### Command headers

An external command describes itself in its first comment block. The block comes after
an optional `#!` line, within the first 80 lines.

```sh
#!/bin/sh
# bromigos:summary=Night light on or off
# bromigos:args=[on|off]
# bromigos:examples=bromigos toggle nightlight on
# bromigos:hidden=true
```

| Key | Meaning |
|---|---|
| `summary` | One line for `bromigos commands` and the generated reference. Every command needs one. |
| `args` | The arguments, in usage form |
| `examples` | An example command line. The key may repeat. |
| `hidden` | `true` leaves it out of listings unless you pass `--all` |

The router ignores unknown or malformed keys. The desktop menu also reads a `menu` key,
which [docs/menu.md](../docs/menu.md) describes.

`bromigos commands --check` reports these problems and exits 1 if it finds any:

| Kind | Meaning |
|---|---|
| `no-summary` | There's no `# bromigos:summary=` line. |
| `shadowed` | A file of the same name earlier in the search path wins. |
| `builtin` | A built-in owns the route, so the file never runs. It isn't reported for the very file a pass-through built-in runs. |

## Migrations

A migration is a script that brings an existing install forward. They live in the
repository's [`migrations/`](../migrations/) folder and ship to
`/usr/share/bromigos/migrations/<id>.sh`.

The id is a 14-digit timestamp, a dash and a lowercase slug, such as
`20261008120200-desktop-user-configs`. `bromigos update` runs the pending ones with bash
after the package step, in id order. Each runs once per user.

A migration gets these environment variables, plus the live session's display:

| Variable | Value |
|---|---|
| `BROMIGOS_MIGRATION` | Its own id |
| `BROMIGOS_CHANNEL` | The machine's channel, or `unknown` |
| `BROMIGOS_SHARE_DIR` | Usually `/usr/share/bromigos` |
| `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` | Set, with the defaults filled in |

A migration must be idempotent, because it may run again after a failure. Its exit code
says what happened.

| Exit | Meaning |
|---|---|
| 0 | Done. It's recorded in `~/.local/state/bromigos/migrations/<id>` and never runs again. |
| 75 (`EX_TEMPFAIL`) | Not yet, for example because its package isn't installed. It runs again on a later update. |
| Anything else | Failed. `bromigos update` stops there, says so, and runs nothing after it. |

A migration never overwrites anything in `~/.config`, because that's yours. It makes what's
missing and reports what it kept. Everything it prints goes to
`~/.local/state/bromigos/migrations/log`.

## The daemons' sockets

The live layer and VECTOR each listen on a Unix stream socket, one command per
connection. You connect, write one command as UTF-8 with no terminator, and read the
reply until the daemon closes the connection.

| Daemon | Socket | Timeout |
|---|---|---|
| The live layer (`ping`, `state`, `toggle`, `mute`, …) | `$XDG_RUNTIME_DIR/bromigos-live.sock` | 4 s |
| VECTOR (`status` returns a JSON object) | `$XDG_RUNTIME_DIR/bromigos-holo.sock` | 6 s |

`bromigos_core::ipc` is the client.

## JSON documents

Most commands print a JSON document with `--json`. Python tools and other programs read
these instead of parsing text.

- Every document has `"schema": 1`.
- Within a schema version, fields are only ever added. Removing a field or changing its
  meaning bumps the version.
- A value that's absent is `null`, never missing.
- A refused change prints `{"schema": 1, "ok": false, "error": "…"}` and exits 1, unless
  a section below says otherwise.

### `bromigos session --json`

```json
{
  "schema": 1,
  "found": true,
  "wayland_display": "wayland-1",
  "hyprland_instance_signature": "0123abcd…_1700000000_123456789",
  "pid": 1234,
  "nested": false,
  "env": {
    "HYPRLAND_INSTANCE_SIGNATURE": "0123abcd…_1700000000_123456789",
    "WAYLAND_DISPLAY": "wayland-1"
  },
  "runtime_dir": "/run/user/1000",
  "candidates": [
    {
      "signature": "0123abcd…_1700000000_123456789",
      "pid": 1234,
      "wayland_display": "wayland-1",
      "running": true,
      "socket": true,
      "nested": false,
      "usable": true
    }
  ]
}
```

- With no session, `found` is `false` and the command exits 1. `wayland_display`,
  `hyprland_instance_signature`, `pid` and `nested` are `null`, and `env` is `{}`.
- `nested: true` means no top-level compositor was running, so it picked the newest
  nested one.
- `env` is ready to merge into a process environment, as in
  `os.environ.update(doc["env"])`.
- `candidates` lists every instance folder with a lock file, newest first. `running`
  means its PID is alive. `socket` means its Wayland socket exists. `nested` means the
  process has `WAYLAND_DISPLAY` set. `usable` means it's running and has its socket.

`session adopt --json` adds this:

```text
"adopt": {"vector_pid": 1350, "vector_signature": "…", "stopped": false}
```

`session hold --json` and `session release --json` print one outcome per compositor:

```json
{"schema": 1,
 "held": [{"user": "tester", "uid": 1000, "signature": "…", "pid": 661, "action": "held",
           "ok": true, "was_off": false, "detail": "…"}],
 "watcher": {"after": 4242, "start": 1791500000}}
```

- `release` prints `released` instead of `held`, and has no `watcher`.
- `action` is `held`, `reloaded` or `not reloaded`.
- `was_off` is the auto-reload setting before the hold. It's `null` for a compositor that
  wasn't held.
- `watcher` is `{"error": "…"}` when the watcher couldn't start, and `null` without
  `--pacman`.

### `bromigos anim --json`

`anim on|off|reset … --json` prints the same document, showing the new state.

```json
{
  "schema": 1,
  "background": true,
  "overrides": "/home/user/.config/bromigos/live/overrides.toml",
  "animations": [
    {
      "name": "intercept",
      "on": true,
      "overridden": false,
      "description": "the burn-in sequence at login and unlock",
      "keys": [
        {"section": "events", "key": "intercept_on_login"},
        {"section": "events", "key": "intercept_on_unlock"}
      ]
    }
  ]
}
```

- `background` is the live config's `[background] enabled`, with your switches merged.
  The runtime switch, `bromigos live on|off`, shows in `status` as `live.background`.
- An animation is `on` when every key in `keys` is true in the merged config. A missing
  key counts as true.
- `overridden` is true when your overrides file sets any of its keys.
- The animations come in listing order.

### `bromigos status --json`

```json
{
  "schema": 1,
  "session": { "…": "the session document above" },
  "live": {
    "running": true,
    "supervisor_pid": 1201,
    "state": "background full target=30fps …",
    "background": true,
    "sounds": "on"
  },
  "vector": {
    "running": true,
    "status": {"pid": 1350},
    "terminal": true
  },
  "animations": { "…": "the anim document above" }
}
```

- `live.running` is true when the supervisor is alive or the socket answers.
- `live.state` is the live layer's `state` reply, or `null` when it doesn't answer.
- `live.background` is `false` when that reply says `background off`, and `null` with no
  reply.
- `live.sounds` is `"on"` or `"muted"`.
- `vector.status` is VECTOR's `status` reply. It's parsed as JSON when it is JSON, else
  kept as a string. It's `null` when the daemon isn't running.
- `vector.terminal` is `false` when VECTOR's terminal is switched off.

### `bromigos profile --json`

`profile set|address|alias … --json` prints the same document, showing the new state.

```json
{
  "schema": 1,
  "path": "/home/user/.config/bromigos/profile.toml",
  "exists": true,
  "you": {
    "name": "Sam",
    "full_name": "Sam Example",
    "aliases": ["sammy"],
    "address": ["Captain", "Sam"],
    "pronouns": "they/them"
  },
  "addressed_as": "Captain"
}
```

- With no profile file yet, `exists` is `false` and every field is `null` or `[]`.
- `address` is in order of preference. `addressed_as` is its first entry, else `name`,
  else `null`. With `null`, VECTOR uses no form of address.
- The file is a `[you]` table with those five keys. A value of the wrong type, or one
  that breaks the rules under [VECTOR, AI and art](#vector-ai-and-art), reads as absent.
- List entries are compared without regard to case.

### `bromigos theme --json`

`theme list --json`:

```json
{
  "schema": 1,
  "current": "wick",
  "current_set": true,
  "themes": [
    {
      "name": "wick",
      "display_name": "Wick",
      "description": "Phosphor green on void: …",
      "mode": "dark",
      "sources": ["system"],
      "error": null
    }
  ]
}
```

- `sources` holds `"system"` for a first-party theme, `"ext"` for an installed
  extension's, `"user"` for yours, or more than one for a theme you layer over.
- `error` says why the theme doesn't load, else it's `null`.

`theme current --json`:

```json
{"schema": 1, "name": "wick", "set": true, "default": "wick", "dir": "/home/user/.local/state/bromigos/theme/current"}
```

`set: false` means no theme was ever set, so `name` is the default.

`theme set --json`:

```json
{
  "schema": 1,
  "name": "wick",
  "display_name": "Wick",
  "dir": "/home/user/.local/state/bromigos/theme/current",
  "rendered": ["dunst.conf", "gtklock.css", "hyprland.lua", "kde.colors", "kitty.conf", "rofi.rasi",
               "startpage.css", "waybar-markup.jsonc", "waybar.css"],
  "from_theme": [],
  "icons": ["clock-amber.svg", "clock.svg", "emblem.svg", "…"],
  "motion": "full",
  "contrast": {"mode": "normal", "ok": false,
               "lowest": {"fg": "selection", "bg": "panel", "ratio": 1.48, "min": 3.0, "ok": false},
               "checks": [{"fg": "text", "bg": "background", "ratio": 15.87, "min": 7.0, "ok": true}, "…"]},
  "reloads": [
    {"app": "waybar", "action": "restart", "pids": [2101], "ok": true, "detail": null},
    {"app": "kitty", "action": "SIGUSR1", "pids": [2207], "ok": true, "detail": null},
    {"app": "hyprland", "action": "hyprctl reload", "pids": [1234], "ok": true, "detail": null},
    {"app": "live", "action": "theme (its world)", "pids": [], "ok": true, "detail": null},
    {"app": "widgets, vector, decks", "action": "palette.json (they watch it)", "pids": [], "ok": true, "detail": null},
    {"app": "hooks", "action": "theme-set.d", "pids": [], "ok": true, "detail": "ran gtk"},
    {"app": "gtklock", "action": "next start", "pids": [], "ok": true, "detail": null}
  ]
}
```

- `from_theme` lists the outputs the theme ships itself. Their templates were skipped.
- `icons` lists the icons written into `current/icons/`. A theme's own icons aren't
  listed.
- `motion` and `contrast.mode` are your accessibility settings, as rendered.
- `contrast.checks` measures each pair of colours that matters. The ratio is WCAG 2.1's,
  rounded down to two places. `min` is what high contrast promises for that pair. `ok` is
  true when every pair passes. `lowest` is the pair with the least margin. Under `normal`,
  the checks show where the theme's own colours fall short.
- `reloads` is `[]` with `--no-reload`. A `detail` says `not running`,
  `no running session`, or why a reload failed. The command exits 1 if any `ok` is false.
- The `hooks` entry appears only when `~/.config/bromigos/hooks/theme-set.d/` has
  programs. Its `detail` names the ones that ran, or each failure's last line.

`theme set` also writes `current/palette.json`, which the widgets, VECTOR and the decks
read. [docs/theming.md](../docs/theming.md) describes it.

```json
{"schema": 1, "theme": "mire", "name": "Mire", "mode": "dark",
 "colors": {"background": "#05090a", "void": "#05090a", "primary": "#b8e05a", "…": "…"},
 "tables": {"holo": {"glow": "#b8e05a", "…": "…"}, "terminal": {"…": "…"}, "widgets": {"…": "…"}, "qt": {"…": "…"}},
 "motion": "full", "contrast": {"mode": "normal", "ok": false, "lowest": {"…": "…"}}}
```

- `colors` holds every colour role and every name in `[colors]`, resolved to `#rrggbb`.
- `tables` holds every other table of `colors.toml`, resolved.
- Under high contrast, both hold the high-contrast colours.
- `motion` and `contrast` are as in `theme set --json`, without `checks`.

### `bromigos ext --json`

`install`, `remove`, `enable` and `disable` print a result:

```json
{"schema": 1, "result": {"op": "install", "name": "hello-deck", "version": "0.1.0",
 "commit": "ec00050…", "detail": "…", "next": ["…"], "plan": {"…": "…"}}}
```

On failure they print `{"schema": 1, "ok": false, "error": "…"}` and exit 1.

A plan, as in an install's or an update's result:

```text
{"op": "install", "name": "hello-deck", "version": "0.1.0", "description": "…",

            "ref": "main", "ref_kind": "branch", "catalog": "https://github.com/bromigos-org/extensions"},
 "commit": "ec00050…", "data_only": false, "warnings": [],
 "parts": [{"kind": "live-deck", "name": "hello-deck", "path": "deck.py",
            "links": [["live/decks/hello-deck.py", "deck.py"]]}],
 "permissions": {"network": "none", "filesystem": [], "code": true},
 "changes": {"from_version", "from_commit", "added", "changed", "removed", "stat", "new_permissions", "new_kinds", "local_edits"}}
```

`changes` appears on updates only.

The other verbs:

| Verb | Document |
|---|---|
| `list --json` | `{"schema": 1, "list": {"extensions": [{"name", "version", "kinds", "enabled", "source", "commit", "status", "problems"?}], "unmanaged_themes": [...], "unfinished"?}}` |
| `info --json` | `{"schema": 1, "info": {"installed", "entry"?, "row"?, "plan"?, "manifest"?}}`, where `entry` is the ledger entry |
| `search --json` | `{"schema": 1, "catalogs": [...], "results": [...], "errors": [...]}` |

Each search result is `{"name", "display_name"?, "description", "kinds", "url", "path"?,

#### The ledger

The ledger is `~/.local/state/bromigos/ext/ledger.json`. It's written atomically, and an
`flock` on `.lock` beside it lets one `bromigos ext` run at a time. VECTOR's guard reads
its `links` and `txn`.

```text
{"schema": 1,
 "extensions": {"NAME": {"name", "version", "description", "source", "commit", "dir", "root",
   "enabled", "installed", "updated",
   "approved": {"how": "data-only|interactive|answers", "when", "detail"},
   "permissions",
   "parts": [{"kind", "name", "path", "links": [{"link", "target", "sha256"}]}],
   "files": {"PATH": "SHA256"}}},
 "removed": [{"name", "url", "commit", "when"}],
 "txn": {"op", "name", "started", "started_unix", "accept": [{"link", "sha256"}]}}
```

`txn` is present only while an operation is under way. An `accept` entry's `sha256` is
`null` for a link being removed.


|---|---|

### `bromigos update --json`

```json
{
  "schema": 1,
  "report": {
    "pacman": 0,
    "packages": [{"name": "bromigos-live", "from": "0.1.0.r4.g47c66b2-1", "to": "0.1.0.r5.gcb25658-1"}],
    "migrations": [{"id": "20261008120200-desktop-user-configs", "outcome": "done", "code": 0, "tail": "made …"}],
    "migrations_ok": true,
    "theme": "tidewell",
    "theme_error": null,
    "previews": "drawing the switcher's previews in the background: …",
    "boot": {"status": "ok", "detail": "…", "commands": []},
    "restarts": [{"what": "live", "action": "restarted", "ok": true, "detail": null}],
    "snapshot": {"pre": 188, "post": 189},
    "channel": "edge",
    "reboot": null
  }
}
```

- `pacman` is pacman's exit code, or `null` with `--no-packages`. When it isn't 0,
  nothing after it ran. Every other field is empty, and the command exits with pacman's
  code.
- `packages` lists every package whose version changed. `from` is `null` for a new
  package, and `to` is `null` for a removed one.
- A migration's `outcome` is `done`, `deferred` (exit 75) or `failed`. `tail` is its last
  lines of output. After a failed one, `theme` and `restarts` are empty.
- `previews` says the theme switcher's previews started in the background. It's `null`
  where there's no renderer.
- `boot` is the boot menu brought up to the theme, with the same `status` values as
  `bromigos boot theme --json`. It's `null` when the update stopped before that step.
- A restart's `action` is `restarted`, `reloaded`, or what you must do, such as
  `log out and back in to run it` or `reboot to run it`.
- `snapshot` is the pre and post pair around the package step. It's `null` when this
  machine has no snapshots, or with `--no-packages`.
- `channel` is the channel the packages came from.
- `reboot` is `null` unless a new kernel or graphics driver waits for a restart of the
  computer. Then it's `{driver, kernel, held, message, notified}`. `driver` is
  `{running, installed, package}`, such as `615.71.09`, `615.78.08` and
  `nvidia-utils 615.78.08-1`, or `null`. `kernel` is `{running, installed: [...]}`, or
  `null`. `held` lists what wasn't restarted or drawn: `live`, `vector`, `previews`.
  `message` is the update's last line, and `notified` says whether the notification went
  out. A held piece's restart has the action
  `held back: restart the computer to run it`.
- `aur` is the AUR step: `{helper, status, detail, command, code, due, changed,
  not_updated, retry}`. `status` is `done`, `none`, `skipped` or `failed`. `retry` is the
  command to try a failed package again. `aur` is `null` with `--no-packages`, or when
  pacman failed.
